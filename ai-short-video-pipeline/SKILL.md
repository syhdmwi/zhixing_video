# AI Short Video Pipeline

## Overview

这个 skill 是总控调度器,不负责把所有细节都自己做完,而是先把任务拆成合适的生产阶段,再决定要调用哪些子 skills。它面向"数字人口播视频"和"画面分镜视频"两条独立生产线,最后在剪辑阶段合流。

默认面向"数字人口播 + 画面分镜 + 剪辑整合"的短视频工作流,而不是只生成单张图或单段视频。

## Beginner First

如果用户明显是第一次使用,或者表达里带有"小白""不会用""不知道怎么开始""你带我走"等信号,不要先讲内部 skill、provider、轨道、队列。

优先把入口改写成用户能直接理解的任务选择。默认先帮助用户判断自己现在想做哪件事:

- 从文案开始做图片
- 从图片继续做视频
- 做数字人
- 从文案一路跑完整流程

第一次回应时,优先使用这种用户视角表达:

- `你把文案发我,我们先从图片流程开始。`
- `你把已经确认的图片发我,我们直接进入视频阶段。`
- `你把音频和人物视频发我,我们直接走数字人。`
- `你把文案发我,我带你从头开始。`

不要第一句话就要求用户理解这些内部概念:

- Track A / Track B
- provider
- 队列文件
- TOS / Bucket / Region
- 子 skill 名称

这些内容只在真正需要解释实现方式时再展开。

## Wake Words

`知行视频skill` 是本工作流的显式唤醒词。

只要用户输入中出现以下表达,应优先进入本总控 skill:

- `知行视频skill`
- `知行视频 skill`
- `知行视频工作流`
- `使用知行视频skill`
- `用知行视频skill帮我制作视频`
- `知行视频skill帮我做图片`
- `知行视频skill帮我做数字人`

如果用户只说了唤醒词但没给具体任务,不要直接解释内部模块,优先用用户入口方式追问:

```text
你想用知行视频skill做哪一步?
1. 从文案开始做图片
2. 从图片继续做视频
3. 做数字人
4. 从文案一路跑完整流程
```

如果用户说的是"使用知行视频skill帮我制作视频",但没有提供文案或图片,优先提示:

```text
可以。你把文案或已经生成好的图片发我,我会按知行视频skill的流程带你做。
```

## When To Use

在以下场景优先使用这个 skill:

- 用户明确提到 `知行视频skill`、`知行视频 skill`、`知行视频工作流`
- 用户要从文案开始规划完整视频工作流
- 用户明确说这件事要拆成多个 skills 分工
- 用户要区分"数字人视频轨"和"画面分镜视频轨"
- 用户最终要把多个生成结果剪进一个完整成片
- 用户明确提到 `nanobanana-2`、`nanobanana-pro`、`seedream-5.0`、`grok`、`即梦 OmniHuman 1.5`、`蝉镜数字人`

## Required Inputs

优先收集以下信息;如果用户没给全,可以按 [references/intake-checklist.md](./references/intake-checklist.md) 的默认值继续:

- 文案全文
- 目标平台和画幅,例如 `9:16`、`16:9`、`1:1`
- 目标时长;若未提供,则需要估算
- 主角信息:人物设定、外貌描述、服装、年龄段、身份、参考图
- 视觉风格:写实、电影感、插画、纪实、广告感等
- 是否使用图片风格预设
- 使用的生图模型、图生视频模型、数字人工具、剪辑工具
- 是否有禁用元素或品牌限制

如果用户已经提供参考图、角色定妆图、品牌规范或既有成片风格,优先以这些材料为准。

## Progress Template

长流程默认要告诉用户"现在走到哪一步了",避免用户中途迷路。

进入新阶段时,优先用这种格式提示:

```text
当前进度:
1. 文案已接收
2. 正在确定风格和比例
3. 下一步会识别重复主体
```

或者:

```text
当前处于:第 3 步 / 共 6 步
正在生成主讲人正面定稿
下一步:确认后生成白底三视图(一张图包含正面+侧面+背面)
```

不要连续多轮只抛结果,不告诉用户当前阶段。

如需统一"小白用户"话术,优先参考:

- [references/user-guidance-templates.md](./references/user-guidance-templates.md)

## State Machine Rule

为了兼容 Trae、OpenClaw、Claude Code 等不会原生执行 Codex skill 状态的工具，本工作流必须按状态机执行。每次被唤醒、用户从中间环节跳入、或用户只回复 `1` / `2` / `全部生图` / `直接生成视频` 等短指令时，都先按状态机检查当前阶段。

执行前必须读取或遵守：

- [references/workflow-state-machine.md](./references/workflow-state-machine.md)
- [references/project-state-template.json](./references/project-state-template.json)

硬规则：

- 如果没有现成项目状态，先根据对话内容保守推断 `current_stage`，必要时初始化一份项目状态。
- 如果用户请求的动作缺少前置条件，不要继续执行，先说明缺少什么，并把用户带回正确步骤。
- 每次进入新阶段时，都要说明当前阶段、已完成内容、下一步和用户可回复的选项。
- `1` / `2` 只能按当前阶段解释，不能跨阶段猜测。
- 如果当前阶段不明确，先用“当前流程状态”格式恢复流程，不要直接生图、生成视频或保存模板。

推荐状态提示格式：

```text
当前流程状态：
阶段：[current_stage]
已完成：[completed_items]
下一步：[next_action]
你可以回复：[allowed_user_replies]
```

## No Shortcut Rule

这个工作流禁止“为了省事而跳步骤”。

尤其在 Trae 这类会自动总结上下文的工具里，必须额外遵守：

- 禁止把“主体确认”和“正式提示词生成”合并成一步
- 禁止把“三视图确认”和“正式生图”合并成一步
- 禁止把“图片确认”和“视频生成”合并成一步
- 禁止因为用户只回复 `1` 或 `2` 就跨阶段推进
- 禁止因为你推断用户“大概率想继续”就跳过确认环节
- 禁止在前置条件未满足时直接提交生图、视频或数字人任务

如果用户说：

- `继续`
- `往下走`
- `开始`
- `全部生图`
- `直接生成视频`
- `做数字人`

先检查状态，再决定是否能执行。

如果不能执行，固定先回答：

```text
现在还不能执行这一步。
缺少：[missing_prerequisites]
下一步你需要先完成：[required_step]
```

## Mode Detection(模式判断)

拿到文案后,先自动判断当前任务的复杂度等级,再决定走简化流程还是完整流程。不要把判断过程暴露给用户,直接按判断结果执行。

### Simple Mode(简化模式)

适用条件(满足任意一条即触发):
- 文案 ≤ 60 秒
- 只有 1 个场景
- 只有 1 个角色(主讲人)
- 无品牌/产品植入
- 用户明确说「快速出图」「先简单做」

简化内容:
- 跳过剧本解析(Step 0),直接从镜头拆分开始
- 跳过空间锁定卡(Step 0.5),只在提示词里隐式描述环境
- 角色三视图可以简化为正面定稿,不强制出完整三视图(正面+侧面+背面)
- 质量审核回环可以简化为只检查角色一致性和瑕疵检测,跳过空间一致性检查
- 风格基因可以只保留 color_palette + lighting_profile + mood_keywords,不强制完整 6 组基因
- 提示词数量 ≤ 12 张时,不要求三分之一纯场景,按文案内容自然分配

但如果文案满足以下任意一条,则**禁止**按 Simple Mode 跳过前期策划:

- 主要内容是抽象概念解释,例如流程、系统、机制、方法论、知识结构
- 核心叙事依赖 A/B 对比、旧方案 vs 新方案、前后机制差异
- 一个观点需要同时串联多个对象关系
- 画面需要大量视觉隐喻才能讲清楚
- 镜头重点不是“谁出现”,而是“机制怎么运作”

### Standard Mode(标准模式)

适用条件:
- 文案 60-180 秒
- 2-3 个场景
- 1-2 个角色
- 有品牌或产品元素

按完整流程执行,无简化。

以下类型默认至少按 Standard Mode 执行,即使字数不长也不允许直接跳到主体清单:

- 抽象概念讲解
- 方法论或系统机制说明
- 多对象关系说明
- 对比型论证文案
- 需要视觉隐喻的科技/知识类文案

### Complex Mode(复杂模式)

适用条件(满足任意两条即触发):
- 文案 > 180 秒
- ≥ 4 个场景
- ≥ 3 个角色
- 有品牌植入 + 产品展示 + 多场景切换
- 用户明确说「完整流程」「精细制作」「系列视频」

额外增强:
- 剧本解析必须完整输出,不得跳过
- 空间锁定卡每个场景必须独立生成
- 质量审核回环每轮都必须执行,包括静帧和视频
- 角色三视图必须完整生成(一张图包含正面+侧面+背面三个视角),每个角色独立出图
- 风格基因必须完整 6 组,不得简化
- 提示词批次建议拆成多个子批次生成,每批 ≤ 15 张,避免单批次过长导致风格漂移
- 建议先生成前 3 张作为风格锚点预览,确认后再批量生成剩余

### Mode Detection 接口

模式判断结果不需要告诉用户,但需要在进度提示中间接体现:

```text
当前进度:
1. 文案已接收
2. 正在确定风格和比例
3. 下一步会识别重复主体
```

如果判断为 Simple Mode,第一轮对话就可以压缩提问轮数(如风格+比例+模型合并确认)。
如果判断为 Complex Mode,第一轮对话就按标准流程逐步确认。

### 抽象概念文案硬规则

如果文案属于以下任意一种:

- 抽象概念解释
- 系统机制说明
- 多对象关系说明
- A/B 对比结构
- 需要视觉隐喻

则必须按 [references/workflow-state-machine.md](./references/workflow-state-machine.md) 推进，并在进入正式提示词前完成这些前置产物:

- 文案接收
- 时长与镜头数估算
- 剧本解析
- 必要的空间锁定卡
- 重复主体清单
- 主体确认
- 三视图生成与确认

硬约束:

- 不允许在剧本解析前直接展示主体清单
- 不允许在空间锁定卡前直接进入三视图
- 不允许把“张数估算 + 主体清单确认”当成已经完成了前期策划
- 如果已经误进入主体清单阶段,应回退并补做剧本解析与空间锁定卡

## Public Asset URL Rule

凡是第三方模型接口要求传入公网可访问资源 URL,本项目默认不要让用户自己处理对象存储。

适用范围包括但不限于:

- 图片参考图
- 图生视频首帧图
- 数字人人物视频
- 数字人音频
- 语音克隆参考音频
- 语音合成后需要继续提交给数字人的音频
- 任何后续模型要求的公网图片、音频、视频资源

默认处理顺序:

1. 如果用户提供的是公网可访问 URL,直接提交给对应模型接口。
2. 如果用户上传的是本地文件,且已配置 TOS,则先自动上传到 TOS,拿到公网直链后再提交给对应模型接口。
3. 如果用户上传的是本地文件,但 TOS 配置缺失,才提示用户补充 TOS 配置或提供公网可访问 URL。

用户侧提示应保持简单:

- `请上传需要使用的图片/音频/视频文件,我会自动转存并提交生成。`

不要要求普通用户理解 Bucket、Region、AK/SK 或对象存储流程,除非当前环境缺少 TOS 配置。

通用上传脚本:

- [scripts/upload_to_tos.py](./scripts/upload_to_tos.py)

## Skill Map

总控 skill 不应和子 skills 重复劳动。先判断任务落在哪个阶段,再调用对应 skill:

1. `ai-video-shot-planner`
   负责文案时长估算、镜头数估算、分镜拆分、数字人与 B-roll 的镜头分配。
2. `ai-video-image-prompts`
   负责基于用户参考图和统一风格生成生图提示词,适配 `nanobanana-2`、`nanobanana-pro`、`seedream-5.0`。
3. `ai-video-prompt-to-images`
   负责在用户确认提示词后,把提示词按顺序转成可执行的生图队列,进入实际生图阶段,并在生成成功后默认直接展示图片给用户确认。
4. `ai-video-series-archive`
   负责把用户已经满意的主讲人、风格、提示词规则和用户选择的正式图样例保存成可复用模板,或者在新文案中先读取指定模板继续生成。重复主体默认随新文案重新识别,不写入通用模板。
5. `ai-video-keyframe-edit`
   负责把已确认的静帧图片通过剪辑方式做成"关键帧轻运镜"的画面轨,默认优先使用 `FFmpeg`。
6. `ai-video-motion-prompts`
   负责把已确认的静帧镜头转成适用于当前视频阶段的图生视频提示词,并默认先产出测试批次动作方案再进入全量执行。
7. `ai-video-generate-videos`
   负责根据当前可用 key 使用 `grok` 真实提交图生视频任务并轮询结果。`seedance` 当前暂时停用。
8. `ai-video-voice-tts`
   负责在用户只有文案、没有成品音频时,先把文案转成可用于数字人的本地音频文件。当前接入速创异步语音合成接口,不是音色克隆。
9. `ai-video-voice-clone`
   负责在用户只有文案、但想用自己的参考音频去读这段文案时,先克隆声音并生成可用于数字人的音频文件。
10. `ai-video-avatar-track`
   负责为 `即梦 OmniHuman 1.5`、`蝉镜数字人` 或速创 `Digital_Humans` 执行数字人生成阶段。
11. `ai-video-edit-assembly`
   负责把"数字人视频轨"和"画面视频轨"合流成最终剪辑方案。

如果用户只要求其中一段工作,不要调用整套流程。

## Workflow

完整主流程阶段顺序以 [references/workflow-state-machine.md](./references/workflow-state-machine.md) 的 `Stage List` 与 `Allowed Transitions` 为唯一权威。本节只描述总控 skill 在各阶段内如何提问、分工和检查，不维护第二套阶段顺序。

### 1. Intake

先确认任务目标是"完整短视频生产包"还是只要其中一段:

- 仅分镜
- 仅图片提示词
- 仅图生视频提示词
- 仅数字人口播整合
- 全流程交付包

如果用户没有说清楚,优先先问"现在想先做哪一步",而不是默认抛完整体系说明。

对新手用户,默认按这个顺序引导:

1. 先收文案或现有素材
2. 再判断是图片、视频还是数字人
3. 再进入该阶段的必要选择

只有用户明确表示"直接走完整流程",才切到全流程节奏。

收到文案后,先自动执行**模式判断**(见 Mode Detection 章节),根据文案复杂度决定走简化流程还是完整流程。模式判断结果不暴露给用户,但会影响后续提问轮数和检查步骤。

在进入人物设定和风格设定前,优先先问一件事:

- 这次是否要复用以前保存过的一整套视频模板

如果用户说要套用模板,优先调用 `ai-video-series-archive` 读取模板摘要,让用户确认后再继续。

如果当前任务要新做一套静帧风格,默认优先用"向导式"问法,而不是一次压给用户多个内部配置项。

推荐提问顺序:

1. 先问风格方式

当前可用模板:
- `AI科普赛博明亮HUD风 请输入 1` - 明亮赛博科技感、HUD 信息图界面、适合 AI 科普和技术讲解
- `手绘水彩教学风 请输入 2` - 温暖手绘、水彩纸纹理、轻松教学氛围、适合知识科普和入门讲解
- `3D科技讲解风 请输入 3` - 商业短视频常用的 3D 科技讲解视觉，人物和信息层并重
- `黑白素描概念讲解风 请输入 4` - 黑白铅笔素描、新闻概念插画感、适合复刻观点口播类 AI 插画视频
- `自主设定风格请输入 0`

2. 再问图片比例

- `16:9 请输入 1`
- `9:16 请输入 2`
- `1:1 请输入 3`

如果用户没有明确选择图片比例,默认按 `16:9` 处理,不要额外卡住流程反复追问。

3. 再问生图模型

- `GPT-Image-2 请输入 1`
- `nanobanana-2 请输入 2`

### 模板加载与全局风格上下文注入

用户选择风格模板(输入 `1`、`2`、`3` 或 `4`)后,必须执行以下步骤,不是只记一个选择:

1. **加载模板**:从 `ai-video-image-prompts/references/style-presets.md` 中加载对应预设的完整风格上下文。当前可选:「AI科普赛博明亮HUD风」「手绘水彩教学风」「3D科技讲解风」「黑白素描概念讲解风」。加载内容不只是预设名,还包括 `style_block`、色彩倾向、光影倾向、材质倾向、环境倾向、构图倾向、负面约束建议,以及可用时的 `visual_style` 结构化字段

2. **展示核确认**:用精简格式展示模板核心特征(风格名 + 色彩倾向 + 光影类型 + 情绪关键词),不要吐出完整 JSON。用户确认后锁定

3. **注入全局风格上下文**:确认后的风格块 + 结构化风格上下文 + 负面约束全局锁定。当前项目后续所有步骤(剧本解析后的提示词拼装、生图)都必须引用这个风格上下文,不得中间重新问「什么风格」

4. **允许微调**:如果用户对某个基因不满意,只修改该基因值,其他保持不变

用户选择自主设定风格(输入 `0`)时,按以下路径:

- 优先按用户明确描述的风格要求执行
- 如果用户给了风格参考图,先分析这张图的整体画风、光影、色彩、完成度和视觉气质
- 如果用户明确说"只参考风格,不参考里面的人物",则只能继承视觉语言,不能继承图中人物设定
- 如果用户同时给了主讲人物三视图或人物参考图,则人物外观必须直接使用用户给的人物参考作为最高优先级,不允许自行替换成新的主讲人物结果
- 收集到足够信息后,同样将风格信息注入全局上下文,项目内锁定

模板加载完成后,继续后续流程(确定比例、模型等),不再重复询问风格。

如果用户本来就熟悉流程,也允许继续接受压缩输入,例如 `1+1+1`。但对第一次使用者,不要默认要求这样输入。

生图模型默认使用数字选择方式:

- 使用 `GPT-Image-2` 请输入 `1`
- 使用 `nanobanana-2` 请输入 `2`

如果用户已经明确指定生图模型,则直接沿用,不重复追问。

### 统一正式生图执行规则

正式生图阶段,无论当前运行环境是不是 `Codex`,都统一走外部脚本 / API 队列方式执行。

执行优先级:

1. 任意环境 + `GPT-Image-2` -> 使用外部脚本 / API 队列方式
2. 任意环境 + `nanobanana-2` -> 使用外部脚本 / API 队列方式

如果用户明确指定执行方式,则以用户指定为准;但默认正式生图不要再走 `Codex` 内建生图。

推荐分工:

- 外部脚本 / API 更适合：
  - 小批量正式生图
  - 大批量正式生图
  - 队列执行
  - 保留任务日志
  - 轮询状态
  - 一镜一任务,降低串图风险

硬规则:

- 正式生图不要再把 `Codex` 内建生图作为默认路径
- 不要因为任务只有 `1` 到 `10` 张,就切回内建生图
- 不要把多个 `shot_id` 合并进一次正式生图请求
- 正式生图必须保持“一镜一任务”的提交方式

对用户侧默认不要解释这层切换逻辑,只需要继续按“已确认提示词 -> 开始生图”的流程执行。

输出语言默认按中文处理,只有用户主动说明"语言为英文"时才切换。

如果用户没有主动指定图片数量,不额外追问张数,默认按文案时长自动估算:

- 默认范围:每分钟 `8~10张`
- 默认按每分钟 `9张`
- 低密度时按每分钟 `8张`
- 普通密度时按每分钟 `9张`
- 高密度时按每分钟 `10张`
- 默认先按普通密度处理
- 只有明显满足高密度特征时才升到高密度,不要因为短句多一点或品牌名多一点就直接判高密度

如果文案里明确出现热门品牌、大众熟知的 logo、地点或标志性物品,这些元素后续应允许直接进入正式画面提示词,不要因为它们没有进入主体锁定流程就被整体过滤掉。

如果某个项目或品牌的核心识别不是文字 logo,而是固定 mascot、吉祥物或 IP 形象,例如 OpenClaw 的小龙虾形象,则应优先把它当作具体视觉主体来处理,而不是只写成抽象品牌元素。

如果文案中的主要主体在社会上本来就有稳定、明显、被大众普遍认知的既有形象,默认优先参考其已有公认形象去制作,不要随意重设计。只有当用户明确要求重设计,或提供新的参考图覆盖旧形象时,才改变该主体外观方向。

如果这些对象属于大众熟知品牌、平台、地标、景区、社会常见标识、服装品牌、汽车品牌、设备品牌,并且用户希望观众一眼认出它们,后续提示词应直接按"明确识别版"处理,例如:

- 官方 logo 清晰可见
- 品牌识别明确
- 工作区标识清晰可见
- 地标特征明确可识别

如果对象较新、较冷门、较垂直、较容易歧义,不要靠猜测写死视觉特征,优先请求参考图、参考链接或更明确说明。

如果存在多个重复主体,后续三视图阶段必须分开生成:

- 一个主体一张三视图(每张图包含该主体的正面+侧面+背面三个视角)
- 不要把多个主体合成同一张三视图

进入正式分镜图阶段后,如果一张图里有多个主体,不要再把多个主体的三视图参考图同时作为强参考挂进去。默认只保留主主体强参考,次主体改用文字约束或品牌/工作区识别元素控制,避免模型误判成设定板或三视图页。

## 主讲人正面定稿与三视图生成规则

**当用户提供参考图时,必须使用垫图(图生图)模式生成**,不允许只用纯文本提示词生图。

具体规则:
- 把用户提供的参考图作为 `reference_urls`(垫图)传入生图接口
- 同时配合提示词指定风格、姿势、背景等要求
- **提示词里不要描述人物五官细节**(脸型、眼睛、发型等),让模型直接从参考图读取
- 提示词只说 "严格匹配参考图中的人物样貌,不要重新设计五官"
- 可以描述:构图(正面/侧面/背面)、服装要求、背景、渲染风格

### 主讲人正面定稿
- 垫图 + 提示词生图
- 提示词示例:"Using the reference image as base, generate a clean front-view full-body portrait of this person on white background, anime illustration style, standing pose, wearing the outfit from the reference"
- 确认后作为后续三视图的参考锚点

### 主讲人三视图
- **一次生成一张图**,图中包含正面、侧面(90度侧脸)、背面三个视角
- 提示词示例:"Character reference sheet, three views on white background: front, side (90° profile), back. Match the person in the reference exactly - do not change facial features, eyes, face shape or hairstyle. Only apply anime art style to rendering. Full body, standing pose."
- 比例建议 16:9,确保三个视角完整展示

三视图展示后,固定提问:

- 需要修改主体请输入 `1`,并直接说明"修改哪个主体 + 修改内容",也可以上传参考图
- 不需要修改请输入 `2`

只有主体确认无误后,才进入正式提示词生成

如果用户要复用已有模板,优先先调用 `ai-video-series-archive` 读取模板,再继续后续流程。套用模板时继承主讲人、风格和提示词规则;新文案中的重复主体仍然重新识别和确认。

### 2. Decide The Two-Track Plan First

先把任务明确成两条生产轨道:

- `Track A`: 数字人口播视频轨
- `Track B`: 图片生成后再转视频的画面轨

当 `Track B` 开始执行时,默认给用户两个分支:

- `图转镜头移动视频模式`
- `图生视频模式`

如果当前任务是要让图里的人物、机器人或环境自己产生小幅动态,默认优先推荐 `图生视频模式`。

如果用户选择 `图转镜头移动视频模式`,优先调用 `ai-video-keyframe-edit`,直接用已确认静帧图片生成轻运镜画面轨。

如果用户选择 `图生视频模式`,再继续走 `ai-video-motion-prompts` + `ai-video-generate-videos`。

在 `图生视频模式` 下,默认执行顺序是:

1. 先给每张已确认静帧判断 `motion_type`
2. 再给每张静帧生成对应的 `video_prompt`
3. 先展示测试批次动作方案
4. 用户确认后再批量提交视频生成

不要在图片确认后直接跳过动作设计阶段提交视频任务。

这两条轨道应分别生成,不要把数字人口播和图生视频混成同一个生成步骤。最后再进入剪辑整合。

正式生图展示阶段还必须遵守以下规则:

- 禁止输出总览图、拼图墙、联系表、批量宫格图
- 无论镜头数量多少,正式分镜图都必须逐张单独展示给用户
- 每张正式分镜图都必须单独附带 `shot_id`、对应原文片段、中文提示词

### 3. Estimate Duration And Shot Count

镜头数默认按每分钟 `8~10` 张图估算,标准情况下按每分钟 `9` 张计算:

- `shot_count = ceil(duration_seconds / 60 * 9)`

时长优先级:

1. 用户明确给出的目标时长
2. 现成音频或数字人口播时长
3. 按文本估算

当只能按文本估算时,默认使用:

- 中文:`230` 字/分钟
- 英文:`150` 词/分钟

可以用 `scripts/calc_shot_plan.py` 做快速估算。

时长估算之后,不要直接进入传统分镜。新的默认拆解顺序是:

1. **文案类型判断**
2. **剧本解析**
3. **信息单元表**
4. **镜头功能 / 视觉承载分配**
5. **镜头配比检查**
6. **只对需要真实空间逻辑的镜头做空间锁定卡**
7. **正式提示词生成**

#### 3.1 文案类型判断

先判断文案主类型,至少归入以下之一:

- `观点输出型`
- `教学解释型`
- `新闻信息型`
- `对比论证型`
- `案例拆解型`
- `情绪叙事型`

这一步决定后面镜头语言应该偏:

- 人物口播
- 概念解释
- 结构图
- 数据对比
- 情绪场景

不要在没做文案类型判断之前,就直接把文案按句子拆成镜头。

#### 3.2 信息单元表

分镜前先把文案拆成**信息单元**,而不是先拆成镜头。每个信息单元至少包含:

- `unit_id`
- `source_text`
- `claim_type`：这句话是在提观点、举例、做对比、给数据、做结论
- `importance`：高 / 中 / 低
- `visual_carrier`

`visual_carrier` 必须使用 3.4 视觉承载层定义的 7 值集合；信息单元阶段只做初判，不另起一套分类法。

信息单元层的目标是先回答:

- 这句话在说什么
- 它在整篇里的作用是什么
- 它更适合由什么视觉形态来承载

不要跳过这一步直接写 prompt。

#### 3.3 镜头功能层

每个正式镜头在生成 prompt 前,必须先定义镜头功能。默认从以下集合里选:

- `hook`
- `setup`
- `explain`
- `compare`
- `evidence`
- `transition`
- `emotion_push`
- `cta`

镜头功能层回答的是:

- 这张图在整条视频里负责什么

不要只写“画了什么”,不写“这张图为什么存在”。

#### 3.4 视觉承载层

在镜头功能确定后,再给镜头指定视觉承载类型。默认至少区分:

- `host_primary`
- `host_with_visual`
- `scene_only`
- `concept_explainer`
- `data_compare`
- `ui_closeup`
- `brand_symbolic`

旧的 `frame_type` 逻辑继续保留,但它现在属于更粗粒度的中间兼容字段。真正的提示词决策优先参考 `visual_carrier`。

兼容映射唯一按下表执行:

| 旧 `frame_type` 兼容别名 | 对应 `visual_carrier` |
| --- | --- |
| `people_primary` | `host_primary` |
| `people_with_scene` | `host_with_visual` |
| `scene_only` | `scene_only` |
| `concept_explainer` | `concept_explainer` |

如果旧队列或外部工具仍要求输出 `frame_type`,只能按这张表从 `visual_carrier` 派生,不得用 `frame_type` 反向覆盖新的镜头决策。

#### 3.5 镜头配比检查

正式提示词输出前,必须先基于 `visual_carrier` 做一次镜头配比检查:

- 默认目标仍是 `scene_only` 约占至少三分之一
- 其余镜头以 `host_primary` 和 `host_with_visual` 为主
- `concept_explainer`、`data_compare`、`ui_closeup` 属于“非纯人物解释镜头”,可以平衡节奏,但不能全部替代纯场景镜头

如果配比明显失衡,优先动作是:

1. 修改对应镜头的 `visual_carrier`
2. 同步改写该镜头的 `visual_goal`
3. 必要时补调对应的 `shot_function`
4. 再重新生成这些镜头的正式提示词

不要等整批正式图片生成完成后,才发现“人物太多”或“场景太多”再被动重跑。

这条规则的优先级低于文案类型判断和信息单元表,也就是说:

- 先服从信息单元决定“这句话适合由什么视觉承载”
- 再服从镜头功能决定“这张图在片子里负责什么”
- 最后才用配比检查做整体平衡

#### 3.6 空间锁定卡的适用范围

空间锁定卡不再默认覆盖所有镜头。只有以下镜头必须做真实空间锁定:

- `host_primary`
- `host_with_visual`
- `scene_only`（真实场景镜头）
- 其它需要稳定摄影空间关系的镜头

以下镜头默认不强制做传统空间锁定,只要求视觉系统一致:

- `concept_explainer`
- `ui_closeup`
- `data_compare`
- `brand_symbolic`

也就是说,抽象解释类文案不应被强行塞进“所有镜头都先按真实空间摄影语言规划”的框架里。

### 4. Create The Immutable Production Bible

在生成任何单镜头提示词前,先固定四块不可随意漂移的全局内容:

- 角色一致性块
- **空间锁定块**(从空间锁定卡继承,包含环境锚点和光线方向)
- 风格一致性块
- 负面约束块

这三块写完后,每个分镜提示词都应继承它们,再叠加镜头自己的动作、场景和构图变化。具体规则见 [references/consistency-rules.md](./references/consistency-rules.md)。

正式提示词默认还应保证环境变化:

- 白天与夜晚穿插
- 室内与室外穿插
- 同一世界观下保留不同空间层次,避免单一场景疲劳

### 5. Split Script Into Shots

把文案按语义节奏拆成镜头,而不是机械按句号平均切分。默认每个镜头 `4` 到 `7` 秒,优先遵守:

- 一个镜头只表达一个清晰信息点
- 开头 3 秒优先服务钩子
- 论证段按观点变化切镜
- 转折句、数字、对比、案例适合单独成镜
- 收尾 CTA 应预留独立镜头

每个镜头至少产出:

- `shot_id`
- `unit_id`
- `time_range`
- `narration_excerpt`
- `shot_function`
- `visual_carrier`
- `visual_goal`
- `image_prompt`
- `image_to_video_prompt`
- `edit_note`

标准格式见 [references/output-format.md](./references/output-format.md)。

### 6. Route To The Right Subskill

按任务内容路由:

- 需要"估时 + 分镜 + 数字人/B-roll 分配"时,用 `ai-video-shot-planner`
- 需要"参考图一致性 + 生图提示词"时,用 `ai-video-image-prompts`
- 需要"提示词确认后进入生图"时,用 `ai-video-prompt-to-images`
- 需要"保存或读取可复用模板"时,用 `ai-video-series-archive`
- 需要"把静帧图片剪成关键帧轻运镜画面轨"时,用 `ai-video-keyframe-edit`
- 需要"静帧转视频动作提示词"时,用 `ai-video-motion-prompts`
- 需要"自动判断视频 provider 并真实提交图生视频任务"时,用 `ai-video-generate-videos`
- 需要"先把文案转成音频"时,用 `ai-video-voice-tts`
- 需要"用用户自己的声音去读文案"时,用 `ai-video-voice-clone`
- 需要"数字人独立视频轨生成方案"时,用 `ai-video-avatar-track`
- 需要"两个视频轨合成最终成片方案"时,用 `ai-video-edit-assembly`

### 7. Generate Image Prompts

生成图片提示词时,按 `prompt-generation-rules.md` 定义的硬结构,将三层数据一次性汇合。不要分别重新描述风格。

**三层汇合规则:**

```
[空间锚点] + [主体] + [动作/状态] + [构图/景别] + [风格基因转写] + [负面约束]
     ↑              ↑            ↑              ↑                ↑                ↑
  空间锁定卡     剧本解析     剧本解析       空间锁定卡     全局风格上下文     全局风格上下文
  (空间层)   (内容层)   (内容层)     (空间层)      (风格层,Step 2)  (风格层,Step 2)
```

- **内容层**(剧本解析产出)→ 填入 [主体] 和 [动作/状态]。只管「谁、干什么、什么情绪」
- **空间层**(空间锁定卡产出)→ 填入 [空间锚点] 和 [构图/景别]。只管「在哪、光从哪来、什么景别」
- **风格层**(Step 2 全局风格上下文)→ 填入 [风格基因转写] 和 [负面约束]。6 组基因 + 负面约束来自已锁定的全局上下文,全项目一致

三层独立供给，在拼装 prompt 时一次性汇合，互不污染。

**构图多样性：** 写完一批提示词后、提交 API 前，必须执行 `prompt-generation-rules.md` §构图多样性强制约束中的自检清单。不通过自检的批次不允许提交。核心原则：每镜的构图必须跟着内容走，不能每镜套同一种句式。

图片提示词必须：

- 保留同一个主角身份、脸部特征、发型、服装主设定
- 保留同一视觉风格、色温、镜头语言和质感
- 只在动作、机位、场景、道具、情绪上做局部变化
- 避免同一批次中无理由更换服装、发色、年龄感、脸型、时代背景

如果用户指定 `nanobanana`、`Seedream 4.6` 等模型,但没有给出该模型的提示词偏好或长度限制,则默认输出"模型无关、结构清晰、可直接改写"的提示词,不假设厂商私有语法。

### 7.5 Quality Review Loop(质量审核回环)

全部静帧图片生成完成后、展示给用户确认之前,先自动运行质量审核回环。

审核内容:
- 角色一致性(脸型、发型、服装是否漂移)
- 空间一致性(环境锚点、光线方向是否跳变)
- 风格一致性(画风、色彩、质感是否突变)
- 构图多样性(景别分布、人物/场景比例)
- 瑕疵检测(多余手指、文字水印、肢体畸形)

审核结果分三级:
- 🔴 必须修改:严重影响辨识度或空间逻辑
- 🟡 建议修改:不完美但不影响整体
- 🟢 轻微可忽略

如果没有 🔴 问题,直接展示报告 + 图片给用户确认。
如果有 🔴 问题,先展示报告,建议用户先处理必须修改的镜头。
如果 🔴 问题 ≥ 30%,建议整体重生成该批次。

用户选择自动重生成时,只重生成 🔴 级别镜头,最多重试 2 轮。

详细审核维度和输出格式见 [references/quality-review-loop.md](./references/quality-review-loop.md)。

### 8. Generate Image-To-Video Prompts

图生视频提示词应建立在已确认可用的静帧上,不要跳过静帧一致性检查。每个镜头的视频提示词至少补充:

- 主体动作
- 镜头运动
- 前景或背景运动
- 节奏和情绪
- 禁止异常变形的约束

如果某个镜头对人物一致性要求特别高,优先先稳住静帧,再做低幅度运动,而不是一开始就要求复杂大动作。

### 9. Run Avatar Generation

当前这一阶段只处理数字人生成,不处理数字人视频在最终成片里的剪辑使用方式。

当全部画面视频已经生成完成后,默认要主动继续问:

- 是否需要制作数字人视频轨

如果用户需要,再进入 `ai-video-avatar-track`,要求用户提供:

- 音频
- 正面人物视频

如果用户上传的是本地音频或本地人物视频,且已配置 TOS,先自动上传到 TOS 并使用生成的公网直链提交数字人接口。只有 TOS 缺失时,才要求用户提供公网可访问直链。

如果用户没有成品音频、只有文案,并且想先得到一条可用于数字人的口播音频:

- 先进入 `ai-video-voice-tts`
- 先把文案转成音频
- 再把音频交给数字人生成阶段

如果用户没有成品音频、只有文案,但明确说要"用我的声音读":

- 先进入 `ai-video-voice-clone`
- 提供参考音频直链和文案
- 先生成克隆后的音频
- 再把音频交给数字人生成阶段

注意:

- 当前 `ai-video-voice-tts` 接入的是速创 `语音合成` 异步接口
- 不是音色克隆
- 当前 `ai-video-voice-clone` 接入的是速创 `语音克隆(同步)` 接口

如果用户没有指定数字人工具,只输出整合方案,不编造某个平台专属参数。

#### 9.5 Video Quality Review

全部图生视频完成后、进入剪辑整合之前,再次运行质量审核回环,这次检查视频产出:
- 人物是否在运动中变形或串脸
- 场景空间是否在运动中跳变
- 运动幅度是否超出提示词约束
- 是否出现不合理的闪烁或抖动

视频质量审核的输出格式与静帧审核一致。

- 生图:`nanobanana-2`、`nanobanana-pro`、`seedream-5.0`
- 图生视频:`doubao-seedance-1.0-pro-fast`
- 数字人:`即梦 OmniHuman 1.5`、`蝉镜数字人`
- 速创数字人:`Digital_Humans`
- 发布平台:抖音、视频号、小红书
- 画幅:根据用户要求选择,不强制固定
